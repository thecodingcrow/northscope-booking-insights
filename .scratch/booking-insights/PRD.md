## Problem Statement

A finance team using SAP-style accounting data has thousands of Documents (journal entries) per period and no fast way to know which ones deserve a second look. Three classes of issue hide in the data:

- **Booking-text mistakes**: typos, whitespace variants, casing differences, and the occasional wrong Vendor selected — invisible until someone spots them by eye.
- **Duplicate Documents**: an invoice posted twice, a payment recorded twice, easily missed when document numbers differ.
- **Inconsistent posting**: a Document booked against an unusual G/L Account, Cost Center, or Tax Code relative to how similar events are normally booked — the kind of thing a careful accountant catches in review but a busy one doesn't.

Today, all three rely on tribal knowledge and manual audit. There is no view that says *"here are the suspicious things in this period and why,"* and no codified record of what *normal* even looks like for this company's books.

A secondary reviewer-of-this-take-home audience also has a problem: they need to evaluate whether this candidate can ship a small, opinionated, AI-assisted product that demonstrates engineering judgment within a tight timebox, with clean PR hygiene and a credible README narrative.

## Solution

A small Next.js web app that ingests a single period of SAP-flavored journal-entry data and renders a **Booking Insights** dashboard with three named features:

1. **Anomaly / typo / near-duplicate check** — surfaces clusters of suspiciously similar Booking Texts with explanations.
2. **Duplicate Booking detection** — surfaces Document pairs/clusters that look like accidental re-postings, transparently scored, with legitimate recurring patterns (monthly rent, payroll) and reversal-then-resplit Documents explicitly distinguished.
3. **Booking Manual (rule suggestions)** — derives 5–10 *antecedent → consequent* rules from the actual data (e.g. *"Vendor V-042 always books to Cost Center IT"*), presents each as a check with evidence Documents and any violators that break the rule.

The dataset is synthetic and generated by the same repository, in two passes: a clean pass that produces valid balanced Documents from a small library of transaction templates, then a corrupt pass that applies a typed **Anomaly Catalog** of 15 deliberately-planted irregularities. Both files are committed; a reviewer can `git diff` to see every planted anomaly in 30 seconds.

The app ships on Vercel with a clickable URL. Code uses English identifiers; data content (booking texts, account names, vendor names) is German to be credible as DACH-market SAP data. The accent palette and layout follow a single direction chosen from a UI prototype (Variant B — "Triage Inbox"): warm stone background, left sidebar nav, generous-whitespace finding cards, severity-coded accents, Geist Sans + Geist Mono for IDs only.

Each of the three features ships as its own PR. After all three land, the README enumerates a self-review of 5 concrete improvements; 2 of those become follow-up PRs. The repo also carries a one-page research write-up on Context Engineering / Knowledge Graphs as a README section.

### Feature 1 — Text similarity

25. As an accountant, I want booking texts compared across the whole dataset after umlaut-folding and whitespace-normalization, so that *"Büromaterial"* and *"Bueromaterial"* and *"Büromaterial "* are recognized as the same intent.
26. As an accountant, I want texts that appear identically on every Line of a Document deduplicated *before* comparison, so that the algorithm doesn't flag the same Document's own lines against each other.
27. As an accountant, I want a flagged result to show the variant texts side by side with a short explanation ("These 3 texts differ by ≤1 character, all on Vendor V-042 — likely a typo cluster"), so that I can act on it without reverse-engineering the heuristic.
28. As an accountant, I want clusters severity-ranked (high = same Vendor, distance 1–2; medium = different Vendors, possibly wrong Vendor selected; low = whitespace/casing only), so that I focus on the worrying cases first.
29. As an accountant, I want each cluster to include the IDs of the Documents the texts came from, clickable to drill in.
30. As an accountant, I want a stable sort order, so that re-running the same input produces the same output (no random tiebreaks).

### Feature 2 — Duplicate document detection

31. As an accountant, I want Documents compared pairwise on five components — Vendor match, amount match, text similarity, primary account-pair match, time proximity — with weights `0.30 / 0.30 / 0.20 / 0.15 / 0.05`, so that the score reflects the audit intuition.
32. As an accountant, I want a "Document Amount" defined as the sum of positive Line amounts (= total debits) per Document, not the signed sum (which is always zero), so that meaningful amounts get compared.
33. As an accountant, I want a pair flagged when the composite score is ≥ 0.75, so that the threshold is consistent and tunable.
34. As an accountant, I want recurring patterns (same Vendor + same amount + same account pair + ≥3 occurrences at ~30-day intervals) automatically excluded, so that monthly rent isn't flagged as duplicate every month.
35. As an accountant, I want reversal-then-resplit Documents (a 1190 EUR invoice that was reversed and re-posted as 595 + 595) recognized via the negative-amount counterpart, so that legitimate corrections aren't flagged.
36. As an accountant, I want the score breakdown shown explicitly per flagged pair (✓ Vendor / ✓ Amount / ~ Text 0.91 / ✓ Account pair / ✓ 1 day apart / − not recurring), so that I see why each pair was flagged.
37. As an accountant, I want pairs unioned into clusters when they overlap (if A↔B and B↔C, show as one cluster of 3), so that I don't see the same Document in two separate pairs.
38. As an accountant, I want confidence rendered as a percentage (`94%`), so that the meaning is unambiguous.

### Feature 3 — Booking Manual

39. As an accountant, I want a small set of 5–10 rules surfaced from the data, each in the form *antecedent → consequent*, so that the system tells me what "normal" looks like for these books.
40. As an accountant, I want each rule shown with: a plain-language description, support count, confidence percentage, 3 evidence Documents (clickable), and any violators (clickable), so that each rule is a self-contained check I can act on.
41. As an accountant, I want only rules with **support ≥ 5** and **confidence ≥ 0.85** surfaced, so that the manual doesn't include coincidences or weak signals.
42. As an accountant, I want a rule with a single-atom antecedent preferred over a conjunction when both have similar confidence and the same consequent, so that the manual stays readable.
43. As an accountant, I want rules over these 8 explicit shapes (and only these): vendor→gl_account, vendor→cost_center, vendor→tax_code, template→cost_center, template→tax_code, template→cost_center-existence, account_range_4xxx→credit_side, account_range_6xxx→cost_center-existence — so that the rules are domain-meaningful, not random co-occurrences.
44. As an accountant, I want violation Documents listed with the antecedent value and the actual (wrong) consequent value, so that the diagnosis is one-click away.
45. As an accountant, I want rules sorted by support descending, then confidence descending, so that the strongest patterns appear first.

## Implementation Decisions

### Architectural shape

- **Single Next.js App Router project**, no monorepo, no backend service. Server components only; no API routes; no client-side data fetching.
- **In-memory data layer**: master data (`accounts.json`, `vendors.json`, `customers.json`, `cost-centers.json`) and the generated `data.json` are imported at module level and held in a server-side singleton. Next.js bundles them at build time. Heuristic results are memoized per-request with `React.cache()`.
- **Six App Router routes**: `/`, `/documents`, `/documents/[id]`, `/anomalies/text`, `/anomalies/duplicates`, `/booking-manual`.
- **Deployment**: Vercel, linked during the structure phase so a live URL is available before features ship.

### Modules (deep)

- **Data generator** — two CLI scripts (`gen:clean`, `gen:corrupt`). Pass 1 instantiates the 10 transaction templates over the 61-day window, producing fully balanced Documents and writing `data/data.clean.json`. Pass 2 reads the clean file + the Anomaly Catalog and applies each planted mutation to produce `data/data.json`. Both files are committed.
- **Anomaly Catalog** — `data/anomaly-catalog.ts` is the canonical 15-entry list of planted irregularities. Each entry has `{ id, kind, target_document_ids, expected_doc_ids, mutation, expected_severity }`. The catalog is read by the generator (for application) and the tests (for assertions). The heuristics do not import it.
- **Data store + views** — `lib/data/store.ts` is the module-level singleton holding `{ lines, documents, accounts, vendors, customers, costCenters }`. `lib/data/views.ts` computes a derived `documents` rollup (per-doc: total debit volume cents, vendor_id if uniform, accounts touched, tax codes, line count, template tag if any) and a denormalized `lines` view.
- **Text similarity heuristic** — `findTextSimilarities(lines): TextSimilarityCluster[]`. Pipeline: normalize (umlaut-fold + lowercase + collapse whitespace + strip punctuation) → de-dupe by `(document_id, normalized_text)` → pairwise compare with `fastest-levenshtein` → score `1 - dist/max_len` and require `dist ≤ 3` for the threshold → union-find cluster → rank severity → generate explanation string per cluster.
- **Duplicate document heuristic** — `findDuplicateDocuments(documents, lines): DuplicatePairCluster[]`. Builds a `DocFeatureVec` per Document, runs pairwise weighted scoring, applies recurring-pattern filter and storno detection, unions pairs into clusters, attaches transparent score breakdown.
- **Rule mining heuristic** — `mineRules(documents, lines): Rule[]`. Enumerates candidates over the 8 explicit antecedent→consequent shapes, computes support and confidence with `Map.groupBy`, applies dominance filter, collects evidence and violations, sorts by support desc then confidence desc.

### Data shape (canonical)

```ts
type JournalLine = {
  document_id: string;        // SAP-style 10-digit, e.g. "1900000123"
  company_code: "1000";
  posting_date: string;       // ISO date

  gl_account: string;
  cost_center: string | null;
  amount_cents: number;       // signed integer cents — see ADR-0001
  currency: "EUR";
  debit_credit: "D" | "C";
  booking_text: string;       // German
  vendor_id: string | null;
  customer_id: string | null;
  tax_code: string | null;
};
```

### Feature 2 — Document feature vector (from prototype)

```ts
type DocFeatureVec = {
  doc_id: string;
  vendor_id: string | null;
  customer_id: string | null;
  document_amount_cents: number;        // sum of positive Line amounts
  posting_date: Date;
  primary_account_pair: [string, string]; // sorted [largest_debit_account, largest_credit_account] by abs amount
  normalized_text: string;
  tax_code: string | null;
  line_count: number;

```

Score weights are locked at `0.30 / 0.30 / 0.20 / 0.15 / 0.05` for vendor / amount / text-similarity / account-pair / time-proximity. Threshold: `0.75`.

### Feature 3 — Atom grammar (from prototype)

```ts
type Atom =
  | { kind: "vendor"; id: string }
  | { kind: "customer"; id: string }
  | { kind: "template"; name: string }
  | { kind: "gl_account_equals"; account: string }
  | { kind: "gl_account_in_range"; range: "4xxx" | "6xxx" }
  | { kind: "cost_center"; cc: string }
  | { kind: "tax_code"; code: string | null }
  | { kind: "debit_credit"; side: "D" | "C" };

type Rule = {
  id: string;
  antecedent: Atom[];     // length 1 or 2
  consequent: Atom;
  support: number;
  confidence: number;
  evidence: string[];     // 3-5 supporting doc_ids
  violations: string[];   // doc_ids where antecedent holds, consequent doesn't
};
```

Only the 8 candidate shapes named in §43 of User Stories are enumerated. `Map.groupBy` does the heavy lifting.

## Testing Decisions

### What makes a good test here

Tests assert **external behavior**: a heuristic, given the corrupted dataset, returns findings whose Document IDs include the expected positives and exclude the expected negatives. Tests do not inspect implementation internals — no probing of normalized strings, no asserting on intermediate scores, no mocking. Each test is a 5–10 line file that imports the heuristic, runs it on the real generated dataset, and asserts on the result shape.

The catalog is the test fixture set. See ADR-0002 — this is golden-master integration testing, deliberately accepted as such.

### Modules tested

- **Data generator output** (`data-integrity.test.ts`) — asserts every Document in `data.json` has signed amount summing to zero. Asserts the file contains the expected number of Documents (~150) and Lines (~450).
- **Text similarity heuristic** (`feature-1.test.ts`) — runs `findTextSimilarities(lines)`. Asserts that the union of cluster doc_ids includes the `expected_doc_ids` from catalog entries `A1`–`A5`.
- **Duplicate document heuristic** (`feature-2.test.ts`) — runs `findDuplicateDocuments(...)`. Asserts cluster doc_ids include `expected_doc_ids` from `B1`, `B2`, `B3`. Asserts the doc_ids associated with `B4` (storno-resplit) and `B5` (recurring rent) do NOT appear in any cluster.
- **Rule mining heuristic** (`feature-3.test.ts`) — runs `mineRules(...)`. Asserts the returned rules cover the 5 rule shapes `C1`–`C5`. For each, asserts the rule's `violations` array contains the catalog's expected violation doc_id.

The Data store and the two formatters are exercised transitively by the heuristic tests; they get no dedicated test files.

### Prior art

This is a greenfield take-home repo — no prior tests to mirror. Test style follows the modern Vitest convention used in current Next.js + TypeScript starters: `.test.ts` files colocated under `tests/`, `import { describe, it, expect } from "vitest"`, no `beforeEach` setup beyond importing the fixture module.

### Out of scope for testing

- No UI tests (React Testing Library, Playwright)
- No coverage metrics or coverage gates
- No property-based testing or fuzzing
- No tests for `formatEUR`, `formatDate`, or the store loader — these are simple and exercised transitively

## Out of Scope

### Scope cuts explicitly called out in the README

- **Multi-currency / FX rates.** Single EUR. The schema carries a `currency` field; adding USD/CHF later is an additive change. Adding it now requires a dated FX-rate table and a per-heuristic decision on transaction-currency vs reporting-currency semantics — not affordable within the timebox.
- **Multi-entity / cross-entity Documents.** Single `company_code = "1000"`. Intercompany flows are a major SAP concept and explicitly not modeled.
- **Cash flow projections, P&L statements, or any business KPI not derivable from postings.** The Assignment forbids this verbatim; the app does not compute any of it.
- **Generic association-rule mining (Apriori / FP-Growth).** Considered (see Feature 3 rationale). Apriori is shape-blind; explicit candidate enumeration over the typed Atom grammar gives more relevant rules and per-doc violation tracking.
- **LLM-generated rule suggestions.** Considered. Adds non-determinism and an API dependency for zero added correctness on a known dataset.
- **Real-data validation of heuristics.** Tests are golden-master against the planted catalog. Real-world validation would be a separate test suite (see ADR-0002).
- **Persistence layer.** Data is read-only and committed as JSON. No database, no migrations, no ORM.
- **Authentication.** No login, no permissions. Demo app.
- **API routes / GraphQL.** Server components consume the in-memory store directly. No public API surface.
- **Client-side state management.** Read-only data; URL search params for filter state on `/documents`; no Zustand, Redux, or React Query.
- **UI / E2E tests.** Heuristic correctness is more important and gets the testing budget.
- **i18n / locale switcher.** UI is English-only; data content is German-only. No runtime locale switching.
- **Mobile-first design.** Desktop-only layout. Mobile would not be unusable but is not designed for.
- **Charts.** The Assignment forbids inventing business KPIs; findings are list-shaped, not graph-shaped. No chart library is added.

### Out of scope for this PRD specifically

- The implementation plan (agent dispatch, parallel batches, review checkpoints) — that's the next artifact, produced by the `writing-plans` skill.
- The self-review findings themselves — those are written after the three feature PRs land.
- The Task 3 research write-up content — written as a final step, captured as a README section.

## Further Notes

### Time budget

The Assignment specifies a 2–3 hour timebox. The build sequence is designed for this:
- Structure phase: ~45 min (10 chore-commits, pushed directly to `main`, no PR review overhead)
- Three feature PRs: ~25–30 min each, dispatchable in parallel by separate agents
- Self-review + 2 follow-up PRs: ~30 min
- Vercel deploy: ~5 min (linked during structure phase, auto-deploys on merges)
- Task 3 research write-up: ~15 min (final step, README section)

Total: ~3 hours with reasonable buffer if parallel agent dispatch works as planned. The brittle steps are shadcn theming (could eat 20 min if it surprises us) and the Vercel deploy of bundled static JSON (should Just Work but server-component bundling is the kind of thing that occasionally surprises).

### What the planted Anomaly Catalog buys us

The catalog is the secret weapon of this submission. It is:
- The **ground truth for testing** — every test assertion ties back to a catalog entry (see ADR-0002).
- The **demo storytelling device** — README can say *"we planted 15 anomalies; here's how each one shows up,"* and the reviewer can verify with a single `git diff data.clean.json data.json`.
- The **signal of engineering judgment** — a candidate who plants explicit anomalies *and explicit negative cases* (B4, B5) is thinking about discrimination, not just recall.

### Use of Conventional Commits and squash-merge

The git log after merge should read as a clean three-act narrative:
- `chore: ...` (×10 — structure phase)
- `feat: text-similarity finder with German-aware normalization`
- `feat: duplicate-document detection with recurring & storno filters`
- `feat: booking-manual rule mining over typed atom grammar`
- `fix: ...` (×2 — follow-up review findings)
- `docs: README with self-review and Task 3 research`

A reviewer skimming `git log --oneline` should be able to reconstruct the work in under a minute.
